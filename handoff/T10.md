## Recorded evidence

### Local custody restoration

- Test first: `npm run verify:backend -- custody-restore` **FAIL** at `fresh-source-process` before adding the worker; **PASS** after wiring fresh-process verification and the Vault wrong-root check.
- `verify-custody-restore.mjs` starts two independent PostgreSQL clusters in a disposable, networkless container using the local Supabase database image. It creates one unfunded Vault fixture using the real T09 migration, takes a `pg_dump` archive, stops the source, and restores the archive with `pg_restore`. The archive and root-key files live separately in disposable tmpfs. The wrong root caused Vault decryption failure; restarting the restored cluster with the retained root succeeded.
- Fresh Node workers queried through `family_custody_worker` before and after the restore. Both matched the pre-backup public address and signed an offline challenge; the parent verifier checked the signature using only that original public key. Wrong actor/family, role, network, address and version returned no seed. Test container and material were removed; no hosted backup, key export, credentials, deployment or Testnet traffic.
- Earlier checks: `npm run verify:backend -- custody-access` and `npm run verify:backend -- contract-baseline` both **PASS**. Prior hosted and financial checks were not repeated.
- Use the [custody backup and recovery contract](../docs/technical-spec.md#t10-custody-backup-and-recovery) for the operator boundary. The grouped Astra checkpoint remains before funded provisioning. No product feature criterion closed.
