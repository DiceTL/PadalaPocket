## Work and acceptance

Implement in these ordered, independently reviewable steps:
1. Reuse R-001 provisioned identity and deployed persistence. Extend its authorization to funding, purchase and private photo routes; enforce ownership on every request. Coordinate the existing login integration with R-003.
2. Implement only Needs funding/accounting: durable operation records, integer money conversion using existing money-mapping.mjs, atomic reservation, payload-bound idempotency, exact signed-envelope/hash persistence before dispatch. Reuse the SDK patterns from proof-sdk.mjs and wallet-backing.mjs without exposing operator scripts directly. Show funded balance only after ledger confirmation.
3. Integrate Groq photo identification using groq-identify.mjs as a reference. One bounded call per explicit photo submission, no automatic retries or rotating credentials. Mock provider responses for automated tests. Bind photo, price, seller and assessment to the immutable purchase. Use minimal live calls for integration/recording and record consumption.
4. Apply finite fixed category/cap rules and balance checks server-side. Above-cap/category conflict/uncertain AI/insufficient funds returns a blocked outcome. No approval workflow in this slice.
5. Authorize a permitted purchase through Noir and claim to the fixed merchant. Persist authorization and claim separately, reconcile unknown outcomes by exact hash and prevent duplicate payment. Return current status and evidence through the frozen API.

Acceptance: authenticated API completes funding and one real photo purchase/claim; negative authorization, duplicate request and unknown-outcome behavior are verified. No signing keys in responses/browser. Failure to meet a timed gate is reported immediately; no fixture success substituted.

### Manual recovery for interrupted setup — DEC-059

**Disabled by DEC-060. Do not run the former closure procedure.** The command now always exits unsuccessfully, and its exported compatibility function always throws before accessing any database or ledger capability. The former `--writers-stopped-and-drained` argument grants no permission.

The current writer persists an envelope through a database request and dispatches it through a separate network request. Existing deployment versions have no shared dispatch fence. Adding a gate check would leave an admission-to-dispatch window unless all writers hold a durable admission through dispatch and recovery can prove they drained. No such guarantee has been established for this deployment setup. A timestamp, operator assertion, or conditional journal update cannot revoke an admitted writer.

Interrupted setup therefore stays processing/unknown with all saved evidence and the one-unresolved-family database constraint intact. Human investigation may inspect a private journal snapshot and exact registration/funding hashes using read-only tools. Do not mark it failed, delete steps, clear the lock, or create replacement funding to bypass it. Missing or unknown evidence remains blocked. The recovery command cannot alter balances or send transactions. Normal exact-funding-hash status reconciliation remains available through the existing authenticated API; registration-only interruptions cannot be closed by this tooling, even after apparent drainage.

Future recovery closure requires a separately reviewed fence and rollout that covers every writer/deployment, handles admitted/crashed writers conservatively, and verifies drainage. No safe recovery closure is offered now.
