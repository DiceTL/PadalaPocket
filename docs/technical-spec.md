# PadalaPocket MVP technical spec

## Current MVP constraints — DEC-093–DEC-100

These are requirements for future contracts, not implemented routes or finalized custody. Up to ten enabled families have isolated app-managed Testnet wallets; additional linked families remain financially unavailable. Independent provisioning, key custody/signing/recovery, pooled Velo accounting and supported reporting interface remain open. See [architecture and target diagram](architecture.md#current-mvp-architecture-target--dec-093dec-099) and [open questions](../work/backend-decision-questions.md).

Deposit contracts must enforce integer PHP centavos, ₱10 minimum and ₱5,000 lifetime cumulative cap, at most one pending deposit per family, and race-safe cancellation of unpaid pending deposits; unknown stays fenced. The deposit lock must not block spending previously confirmed funds. Reject insufficient safely available project funds rather than fabricating credit. Operator-only cap visibility, accessible XLM alongside primary ₱ display and the fixed ₱9.68/XLM confirmation are product requirements.

DEC-102 requires a family-bound checkout, verified Velo and Stellar payment evidence, uniqueness of the underlying payment, backed project-funds reservation and a confirmed transfer to the family parent wallet before availability. Persist transaction identities and retain unknowns; a timeout or cancellation request alone proves neither failure nor nonpayment. Exact evidence retrieval, atomic admission, balances and dispatch/recovery contracts remain unresolved.

Disabling is explicitly operator-authorized, not automatic: block new operations, reconcile uncertain work, return confirmed recoverable funds to the project wallet and free the slot only after confirmation, preserving necessary records/keys. Unavoidable reserve/fee treatment and exact cleanup semantics remain open; never imply impossible recovery or seller recycling. Disabled families cannot re-enable; account reuse in a new family needs isolation and a fresh cap. Operator queries are noninteractive and agent-readable; mutations require authorization, preview and confirmation. Error history includes resolved significant errors for 30 days, newest first, with credentials, keys, photos and PII redacted; financial journals are not automatically deleted.

Seller claim and aggregate withdrawal are separate durable facts. Attempt withdrawal when confirmed withdrawable balance reaches the current anchor minimum, batch no greater than its maximum and stop on failure/unknown without unsafe retry. No per-purchase attribution without evidence; student access is limited to their own claim and sanitized seller summary. Unattended interactive SEP-24 and precise fees/reserves are unresolved.

Notification contracts must target the student for insufficient selected bucket and post-success zero bucket; weekly reminder targets both roles. The two-step demo reminder/event must not rewind time, must supersede the old schedule when changed before the event, use the latest saved allowance amount when the event begins, and leave network/approval clocks real. Under DEC-100, prevent parent allowance amount or schedule changes while either advance action is running in both UI and server, including direct API and concurrent requests; do not infer a blanket block on other settings. Define and prove atomic admission/change race handling, event identity/replay, and safe lock timing for failed, interrupted, unknown and resumed operations; these mechanics remain unresolved. AI/login/dashboard latency are user observations requiring measurement; do not suppress failures or assume a model/key expiry.

DEC-101 requires a student-initiated cancellation boundary during photo assessment: a cancelled assessment's late response cannot advance purchase execution. After cancellation or failure, retry begins with the student providing photo and details again. The API/state contract, durable cancellation-versus-assessment/payment admission and race handling remain to be designed and verified; aborting a browser request alone does not establish cancellation. Model/provider and additional assessment context remain undecided.

## Connected-function contracts — L-001 / DEC-071

L-001 adds `GET /api/family/rules` for trusted parent/student family members and parent-only `PUT /api/family/rules` with `{expectedRevision,settings}`. Settings contain integer-centavo strings `weeklyAmountMinor`, `capMinor`, integer `needsPercent` (0–100), and unique catalog IDs in `needsCategories`/`wantsCategories`. Stored revisions use compare-and-swap; stale edits return 409 RULES_CHANGED. Categories use the existing six photo-demo IDs. No row means revision 0 with the existing ₱4.84 Needs policy. A database insert trigger snapshots saved rules onto future purchases; past purchases retain their rules. Weekly amount/split are setup data until backed allocations/scheduling are implemented; no automatic transfer is triggered by settings writes.

`GET /api/family/activity` is read-only: parent reads family Needs purchases, student reads their own Needs purchases. Returns at most 100 newest items with status, reason, seller, amount, AI product/category, timestamp and a relative `photoPath`. No photo bytes, signed envelopes, raw provider diagnostics or private-money activity. Photos use the existing authenticated `GET /api/purchases/:id/photo`; browser fetches with bearer Auth and renders a temporary object URL. These routes are implementation work, not deployed acceptance evidence; see L-001.

## Architecture reference

The working stack, component diagram, boundaries and unresolved physical money routing live in [architecture](architecture.md). This spec owns the detailed data model, HTTP contracts, execution/recovery and verification requirements. Update architecture alongside any architectural decision under DEC-031.

## Ownership and trust

- Browser: sign in through Supabase Auth, collect inputs, upload a photo through a restricted signed upload, and display server-returned outcomes. Never write balances, roles, approvals or settlement status directly.
- API: validate the access token with Supabase Auth, load trusted parent/student membership, enforce object-level access, run rules, call AI/payment services and return role-filtered data. Derive identity from authentication, never a request's `parentId` or `role`.
- Postgres: authoritative application rules, requests, bucket accounting, reservations and operation history. Use transactions for monetary mutations and unique constraints for duplicate prevention. Ledger-confirmed transfers are authoritative for on-chain holdings; database balances must reconcile to them.
- Supabase service credentials and all signers remain server-only. Privileged database access bypasses RLS, so every API handler must authorize its caller before using it. Enable RLS and restrictive grants on every exposed table; no browser financial writes.
- Private photo objects belong to the purchase/student. The linked parent may view allowance photos; unrelated users cannot. Authorize before issuing short-lived read URLs. Validate image type, decoded content and size; exact limits depend on provider/hosting selection. Do not log photos, tokens, signed URLs or secrets.
- Use two separate real demo logins, not an unauthenticated parent/student role switch. My Money fields/transactions are excluded from parent queries, API projections, notifications and aggregates. App privacy does not conceal public Stellar activity or grant privacy from the server operator.

Supabase access behavior is documented in [RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security) and [private bucket guidance](https://supabase.com/docs/guides/storage/buckets/fundamentals). No project permissions have been configured or tested.

## Logical data model

Proposed tables, not migrations. UUID identifiers; UTC timestamps. Keep private financial tables unexposed where possible; selectively expose only what browser Auth/Storage requires.

| Table | Essential fields and invariants |
|---|---|
| `family_members` | `family_id`, `user_id`, trusted `role`; one demo parent/student; server-controlled membership |
| `allowance_rules` | student, weekly amount, Needs ratio, cap, category sets, schedule/timezone, `version`; snapshot version on purchase |
| `wallet_accounts` | user, purpose, Stellar address, Noir device reference if applicable; never private keys; physical layout gated below |
| `balances` | student/parent, bucket, available and reserved amounts, revision; nonnegative; My Money student-only |
| `purchases` | student, bucket, seller reference, entered price, mapped Testnet amount, immutable photo reference, AI assessment, rules version, approval reason, expiry, status, revision |
| `savings_requests` | student, amount, parent decision, status, release operation; one release per approved request |
| `money_operations` | unique action/idempotency key, owner, request fingerprint, transfer kind, debit/credit, reservation, state, nonce, signed-envelope reference, transaction hash/result; restrict sensitive envelope access |
| `notifications` | recipient, event, safe payload, read time; no My Money purchase events for parent |
| `demo_clock` | demo instance, simulated time, revision; scheduled events deduplicated through operation keys |

Money crosses JSON as decimal strings, never floating-point amounts or JavaScript BigInt. Proposed UI price is integer PHP centavos (`priceMinor`); ledger amounts are integer stroops (`amountStroops`). Server computes the mapping and records its version; browser cannot choose a ledger amount independently. The demo conversion ratio, rounding and cap comparison unit require team acceptance before payment implementation. Label any peso equivalent as simulated. Keep fees/minimum account reserves separate from spendable bucket funds.

Each bucket must have an auditable backing relationship. Candidate: Needs/Wants as app sub-balances of Noir escrow, with Savings and My Money isolated from allowance spending. Physical accounts, escrow withdrawal rules and weekly transfer routing are **not yet proven**. Do not show a database-only allocation as an on-chain transfer or implement rollover before its actual signing/transfer path is established.

### T05 durable money journal — DEC-104

The additive foundation uses `money_operations`, one `money_reservations` row per operation and `money_signed_steps`. T08 integrates current writers with T06 dispatch and T07 reconciliation; hosted cutover remains incomplete. A hold record does not prove sufficient backing or authorize a transfer.

- `admit_money_operation` is coordinator-only after T08. Validate current actor/family membership; use unique `(family_id, request_key)` across purposes. Bind actor, purpose, `testnet`, `native`, source/destination references, signed-64-bit integer stroops and a JSON-object request payload. Amount is positive except explicitly zero-principal `device_setup`, which requires zero and retains a zero-value hold (DEC-109); preexisting positive setup rows are not rewritten. Compare every bound field on replay, not merely the fingerprint; canonical JSONB ignores object-key order. Compute a SHA-256 request fingerprint in Postgres. Admission inserts the operation and its one hold in the same database transaction.
- Money crosses the RPC/helper boundary as canonical decimal strings, including values beyond JavaScript's safe-integer range. Source/destination references identify resources; they do not select new physical wallet routing.
- `record_money_signed_step` is service-only and checks operation/family binding. Unique operation/stage and unique Testnet/transaction hash prevent changed-stage replay or transaction reuse. Persist exact envelope, hash and source public account before any future dispatch; replay must match all fields. T05 records immutable inputs, not a claim that an envelope has executed or passed signing authorization.
- All three tables have RLS and no browser grants. Only RPCs insert; application roles cannot update/delete. Immutable-row triggers also reject owner-level mutation. T08 removes legacy service-role access to saved envelopes and moves financial RPCs to the coordinator role. There is no release, credit, dispatch or reconciliation transition in T05 itself.
- `money-journal` uses real isolated local Postgres and existing verification memberships. Exercise concurrent admission/conflict, failed-hold rollback, integer fidelity, tenant binding, step identity and denied browser access. Synthetic saved bytes are storage fixtures, not live-provider evidence. See [T05](../handoff/T05.md) for observed results and limits.

### T06 coordinated dispatch — DEC-106

The additive coordinator uses durable `money_dispatch_steps` and per-Testnet-source `money_dispatch_sources` in existing Postgres. It does not select family keys, approve payments, establish backing or cut over existing writers.

- Service-only RPCs serialize preparation per source and bind operation/family, stage and source. One invocation acquires preparation authority once; subsequent workers cannot sign a replacement. Claims have no automatic expiry or takeover. Unmanaged T05 saved steps are not silently adopted.
- The backend verifies a normal Stellar transaction's selected source signature under `Networks.TESTNET`, positive sequence and finite time bounds before saving canonical signed XDR through the T05 journal. No fee-bump envelope is supported by this boundary. The dispatch RPC returns the saved bytes, never a newly prepared replacement.
- A separate durable compare-and-set grants send authority once. Persist it before calling the transport. Another worker may dispatch a saved-but-not-send-claimed step; after send admission, workers only query the saved hash. Paused/crashed workers never create lease-based replacement authority.
- Only matching successful RPC evidence (exact hash/envelope, positive ledger, `txSuccess`, and one successful matching inner result per operation) creates an idempotent confirmed checkpoint and atomically clears that source's active pointer. Historical checkpoint replay cannot clear a newer source owner. Failures, missing evidence, timeouts and `NOT_FOUND` do not free sources or holds.
- No database transaction spans signing or an external request. Default transport is Stellar Testnet RPC with bounded requests; application roles have no direct writes or RPC execution. Existing T05 immutable identity/envelope records stay unchanged.
- `dispatch-boundary` proves real local database coordination across separate Node processes, including paused preparation/send owners, saved-envelope resume, conflicting sources and confirmed-checkpoint replay. Disposable signing keys stay in memory; expired envelopes use a historical clock and a controlled loopback RPC fixture. This proves boundary behavior, not live Testnet settlement. T07/T08 and the grouped review remain required before risky use.

### T07 exact-identity recovery — DEC-107

`read_money_recovery` is a coordinator-only, family-bound snapshot after T08; `reconcileMoneyStep` is backend runtime code, not a public route or dispatcher. Current T08 adapters use it only to observe existing managed stages.

- Derive source, network, exact envelope and hash from stored operation/stage records. Never accept a replacement transaction identity from the caller. A snapshot read creates no claim, reservation or signed step.
- Missing/unmanaged stages, interrupted preparation and saved-but-not-dispatch-admitted stages remain fenced. Reconciliation never starts a missing stage or acquires send authority.
- For dispatch-admitted work, validate the saved normal Testnet transaction/source signature and finite validity bounds, then make one bounded saved-hash lookup. Expiry alone neither proves failure nor prevents confirming a historical success.
- Confirm only independently matching envelope hash and exact bytes, a positive ledger and consistent successful result/operation XDR. Reuse T06's idempotent checkpoint; concurrent observations and lost checkpoint responses cannot release a newer source owner or confirm twice.
- Timeouts, transport/malformed responses, `NOT_FOUND`, failed transactions and contradictory evidence leave principal holds/source fences unchanged. A known failed stage alone does not prove an entire multi-leg operation can release principal.
- Verify retained checkpoint evidence locally before returning confirmed. A provider retention gap cannot erase an already verified checkpoint. Recovery outputs omit envelopes, signing material and provider diagnostics.
- This boundary does not credit balances, release principal or implement general/operator repair. Path-specific live/deployed recovery, T08 cutover and grouped review remain required. See [T07 evidence](../handoff/T07.md).

## Proposed HTTP contract

All routes below are PadalaPocket routes to implement, not claims about vendor APIs. Require a bearer access token. State-changing requests carry `Idempotency-Key`; reuse with a different body returns `409 IDEMPOTENCY_CONFLICT`. Persist intent before external side effects. Server checks ownership on every identifier. Return amounts as strings and timestamps as ISO 8601 UTC.

| Route | Caller and input | Output / effect |
|---|---|---|
| `GET /api/me` | Authenticated user | Trusted role, safe family context, permitted balances/rules; parent response excludes My Money |
| `PUT /api/allowance-rules` | Parent; settings and expected rules version | Validated settings/new version; existing-purchase rule-change behavior remains gated |
| `POST /api/photo-uploads` | Student; MIME type, byte count | Restricted object path and short-lived upload authorization; finalize/validate before AI access |
| `POST /api/purchases` | Student; bucket, category, seller ID, price, photo object | Purchase ID, decision/status, safe AI result and approval expiry if applicable; My Money omits category/photo |
| `PUT /api/purchases/:id/photo` | Owning student; new photo, expected revision | Only allowed from `needs_photo`; invalidate prior assessment, increment revision and reassess |
| `GET /api/purchases/:id` | Student or permitted parent | Current state, permitted evidence and confirmed transaction references |
| `GET /api/approvals` | Parent | Own linked student's pending purchase/Savings requests; no My Money purchases |
| `POST /api/purchases/:id/decision` | Parent; `approve`/`reject`, expected revision | Exact request accepted or conflict/expiry; approval does not imply ledger confirmation |
| `POST /api/savings-requests` | Student; amount | Pending request; no funds released |
| `POST /api/savings-requests/:id/decision` | Parent; decision, expected revision | Release operation or rejection; success only once release is complete |
| `GET /api/notifications` | Authenticated recipient | Recipient-only app notifications |
| `POST /api/demo/advance` | Parent on demo instance; target time, expected clock revision | Due event outcomes, updated clock; unresolved submitted payments block affected rollover |
| `POST /api/demo/merchant-claim` | Parent as explicit demo operator | Claims through fixed demo seller signer; never arbitrary caller-supplied merchant keys |
| `POST /api/demo/withdrawals` | Parent as explicit demo operator; amount | Test-anchor interactive URL/withdrawal ID after authenticated initiation |
| `GET /api/demo/withdrawals/:id` | Authorized demo operator | Actual anchor status, kept distinct from claim and simulated fiat completion |

Demo operator permissions are a proposed convenience for the single controlled seller, not a seller onboarding product. Seller lookup/QR parsing must resolve to the fixed Testnet seller. Entered GCash details remain synthetic metadata, never a claim that the GCash number received payment. Arbitrary GCash QR interoperability is unresolved.

Example allowance request:

```http
POST /api/purchases
Authorization: Bearer <student-access-token>
Idempotency-Key: <unique-client-action-id>
Content-Type: application/json

{"bucket":"needs","category":"meals","sellerId":"demo-seller","priceMinor":"7500","photoObject":"<owned-validated-object>"}
```

Example parent-review response (illustrative, not observed):

```json
{"id":"<purchase-id>","revision":1,"status":"awaiting_parent","reason":"CAP_EXCEEDED","ai":{"productName":"Rice meal","category":"meals","identification":"identified"},"expiresAt":"<server-generated-UTC-time>"}
```

Use `201` for a newly persisted request, `202` for external work in progress, and `200` for a read or repeated identical action. Technical errors use `{ "error": { "code": "...", "message": "...", "retryable": false } }`: `400 INVALID_INPUT`, `401 UNAUTHENTICATED`, `403 FORBIDDEN`, `404 NOT_FOUND`, `409 STALE_REVISION`, `409 APPROVAL_EXPIRED`, `503 PROVIDER_UNAVAILABLE`. Normal product outcomes such as insufficient bucket funds are persisted purchase decisions with reason codes, not network errors. Never describe an unknown submission as safe to repay.

## Purchase execution and recovery

1. Validate student, bucket, price, recipient and photo ownership. My Money skips AI/parental rules; retain balance and technical checks. Run the selected-bucket sufficiency check first.
2. B-004 proof candidate is Groq `qwen/qwen3.8-27b` under DEC-050; the operator-only script does not implement this product flow. For allowance, call real image AI and validate structured output: product name, supported category, `identified`/`uncertain`, concise supported reason and any alcohol/tobacco flags. Image text is untrusted input. AI cannot invoke signing tools. No reliance on a fabricated numeric confidence score; assess behavior on sample images before choosing thresholds/model.
3. Uncertainty yields `needs_photo`; insufficient selected-bucket funds yields `rejected` and a student notification, not a parent notice (DEC-097). Identified category conflict, prohibited-item flags or over-cap yields `awaiting_parent`; otherwise proceed to payment preparation.
4. Bind approval to a server-stored fingerprint of recipient, amount, bucket, photo content reference, AI result and rules version. Parent decision uses a conditional revision/status/expiry check. Freeze request fields once awaiting approval; edits require a fresh request and assessment. Recheck balance and policy before execution.
5. Atomically reserve bucket funds when entering `ready`, then persist a unique payment operation/nonce before network submission. Pending parent requests are not guaranteed funds; insufficient funds at approval/execution denies payment. No database transaction remains open during an HTTP/ledger call.
6. Proposed states: `assessing → needs_photo | awaiting_parent | ready | rejected`; `awaiting_parent → ready | rejected | expired`; `ready → submitting → merchant_pending | failed | unknown`; `merchant_pending → claimed` after confirmed seller claim. `unknown` may resolve to confirmed or failed after reconciliation. Claim failure leaves merchant pending funds, not an automatic student refund.
7. Reserve until confirmed debit or definite failure; never release on timeout alone. Persist the signed-envelope reference/hash before submission where available. Reconcile an existing hash/nonce before any retry. Classic source-account sequence collisions require serialized submissions for that signer. DB transactions/unique keys protect concurrent approvals, allocations and releases; an in-memory lock cannot coordinate Vercel instances.
8. Return `202` with purchase ID when external work exceeds the bounded request wait. Next authorized status request can perform bounded reconciliation of already recorded work; no fire-and-forget process after the function returns. Poll only while a visible request is pending. Prove hosting duration and recovery behavior before relying on this design.

All approval expiry checks use server-authoritative application time. Demo time may advance an expiry but never extend a request past its real 10-minute safety deadline; keep a separate real deadline. Network policy expiry and transaction validity always use real ledger time. Weekly ordering, skipped funding, category overlap and other proposed product defaults remain in the product spec; this document does not approve them.

## Signing and integration proof

Before full family Auth exists, follow the temporary operator-only proof protection in [architecture](architecture.md#responsibilities-and-boundaries). A proof endpoint must reject missing/wrong authorization before any signing/network action. Disable that route when the application Auth task is complete; do not expose its credential to the web app.
