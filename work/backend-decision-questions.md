## Remaining questions and feasibility

- [ ] **Velo supported reporting interface — investigate:** Is there a documented, supported merchant SDK/API to report an app-managed payment and reliably observe its intent? [EV-027](evidence-ledger.md#ev-027) observed one 0.10-XLM Testnet payment as paid using the public frontend reporter, not a verified supported merchant interface; no replay or production support is established.
  - [EV-030](evidence-ledger.md#ev-030): the normal checkout API omitted the hash, while an undocumented public query returned the verified hash for the existing proof. App-managed signing can retain its own hash before dispatch; provider support remains unconfirmed.
- [ ] **Pooled Velo and accounting — investigate/design:** Is a shared project/receiver supported for multiple families? Define authenticated intent/receipt → exactly one family → confirmed backed credit, entitlement reservations, isolated-wallet transfers and partial/unknown handling. Prove repeat/concurrent exactly-once credit against the real database; checkout status and a shared receiver balance cannot mint spendable family balances. No pooled family credit is implemented.
  - [Nov 14 bounded checks, EV-028](evidence-ledger.md#ev-028): actual handler with isolated auth/database contexts separated two families' checkout histories and reused a paid intent on repeated confirmation. Only checkout-status fields were updated; no family credit exists in that path. Live Velo receipt read succeeded; deployed database isolation, concurrent credit and pooled backing were not tested. No new payment was sent.
- [ ] **App-managed keys and family funds — investigate/approve design:** Choose and verify secure storage, access/recovery authority, family/network/purpose signer bindings, exact account/device topology, provisioning, fees/reserves/backing and partial-transfer/refund handling. Bucket IDs are not separate Stellar accounts. Preserve accepted parent-owned Needs/Wants/Savings and distinct student My Money authority; establish shared-seller coordination before changing global admission. The user selected isolated app-managed wallets, not a key-store provider, encryption scheme or account count. See [architecture](../docs/architecture.md).
  - [Wallet feasibility investigation, EV-029](evidence-ledger.md#ev-029): ten synthetic families produced distinct bucket IDs and integer-conservation checks passed, but current providers still use global signers. Read-only Testnet reserve inputs are measured; full provisioning costs are not. Custody/restore, signer bindings, shared-seller coordination and safe dispatch recovery must be established before a funded family test. No wallets were created; key-store/topology suggestions remain proposals.
  - [EV-030](evidence-ledger.md#ev-030): zero-row public/server Data API probes found `vault` schema unexposed; installation, SQL privileges and actual restore remain unverified.
  - **Proposed next bounded test, not executed or architecture approval:** once the storage/provider, access and backup/restore prerequisites are chosen/configured, use a disposable unfunded key to prove store, restart/fresh-runtime restore, public-key match, message signing/verification, unauthorized retrieval/signing denial and no secret/envelope leakage. This needs no financial provisioning or readiness flip. Only after custody/restore and a scoped dispatch/provisioning contract are established should an explicitly authorized funded family test proceed. No credentials or storage material are selected or changed by this checklist.
- [ ] **Deposit cancellation:** Define provider cancellation and payment-race semantics and evidence sufficient to conclude unpaid; unknown stays blocked and previously confirmed funds remain usable.
- [ ] **Fees, reserves and cleanup — investigate/design:** Determine precise spendable calculations, measured provisioning/operation costs, safely recoverable funds and disable sequencing. Keep necessary keys/records; unresolved operations block unsafe recovery/slot release, and registry ownership must remain available for escrow recovery. Prove ten-slot admission/overflow, confirmed capacity reuse and disabled-family create/join-new-family behavior under DEC-095; do not promise full fee/reserve recovery or seller recycling.
- [ ] **Shared seller Noir claims and SEP-24 — investigate/design:** Establish how concurrent family claims aggregate into the one seller's withdrawable funds, including claim/withdrawal signer serialization and sanitized student projections without unsupported per-purchase attribution. Can the reference anchor's interactive flow satisfy the accepted automatic post-claim intent and safely resume unattended? Verify current minimum/maximum, accumulation, batching, failed/unknown stop and actual app status evidence; [EV-020](evidence-ledger.md) records 1–10 XLM on 2026-11-06, which may change. Operator proof is not app completion; fiat remains simulated.
  - [EV-030](evidence-ledger.md#ev-030): latest observed 1–10 XLM bounds are time-sensitive; disabled fee endpoint does not mean zero fees. Unattended operation remains unverified.
- [ ] **Recovery and authority — investigate/approve design:** Define evidence and authorized continuation for uncertain Velo, transfers, purchase/claim, approval, weekly and withdrawal operations; establish cross-worker/cross-deployment admission, dispatch fencing and shared-signer/seller coordination before retry or release. Missing hash/`NOT_FOUND`, request timeout or a database flag does not prove an admitted dispatcher stopped. Keep exact saved identities, holds and financial gates; never repair by disabling Auth, flipping `wallet_ready` or inventing a replacement transaction. [Current safety boundary](../handoff/R-002.md).
- [ ] **Weekly admission and safety — investigate/design:** Define atomic handling of races between allowance amount/schedule changes and either demo advance, event identity/replay, and safe lock timing for failed, interrupted, unknown or resumed operations. Preserve the DEC-100 restriction without assuming a particular lock mechanism or duration.
- [ ] **AI diagnosis and targets — investigate, then team choice:** User reports uncertain/unavailable and latency issues; possible expired Groq model/key is unverified. Measure real images, configured provider access and component latency, evaluate privacy/cost/accuracy, then agree measurable targets and any provider/model change; never hide degraded results. No arbitrary accuracy/latency threshold or replacement provider is selected.
- [ ] **Login/dashboard targets — investigate, then team choice:** Measure Auth, API/database, ledger/provider and browser timings, then agree measurable targets and fix demonstrated bottlenecks without weakening access or presenting stale funds as confirmed. This is diagnosis, not permission to bypass login.
- [ ] **Onboarding details — team choice last:** Confirm account-specific guidance, trigger, progress, completion and resume once functional journeys are stable. Founder handles functional bare tutorial pages/routing last; frontend/design owns visual presentation. Per-account persistence is required, but a particular table/storage design is not already approved.

Further implementation sequencing and authorization belong in the implementation plan and scoped handoffs, not this discussion checklist.
